# Read-only offline application release-source check

Use this application-side helper to check a **selected extracted bundle** against
the reviewed commit and inventory digest recorded at trusted staging. It is not
Git/Internet dependent and is automatically included by the current builder's
existing `dashboard/` source copy. No builder, Ansible or Splunk changes are needed.

## Establish expected values independently

1. Choose the reviewed milestone candidate under the
   [promotion checklist](milestone-release-checklist.md).
2. Patrick builds/downloads the matching offline artifact and verifies it using
   the existing [bundle procedure](offline-bundle.md). Confirm the workflow's
   resolved commit and `inventory.json` revision agree with the candidate.
3. In that trusted, verified staging copy, record the archive SHA-256 **and** the
   SHA-256 of `inventory.json` (for example, `sha256sum inventory.json`). Preserve
   the expected commit and inventory digest separately from the target copy.
   Inventory's digest is also recorded in the original `SHA256SUMS` file.
4. Transfer through the approved route. Compare the target against those saved
   expected values. Do not derive the baseline from an unknown or changed target
   and then call that independent verification.

Expected hashes are integrity anchors, not signatures or proof that a workflow,
commit, supplier or licence is approved. Follow the owner review/transfer process.

## Inspect before installing or starting source

From the pristine extracted `netstrike-offline-bundle` directory on the supported
Linux target, substitute the saved 40-character lowercase commit and 64-character
lowercase inventory SHA-256:

```sh
PYTHONPATH="$PWD/source" python/bin/python3.11 -B -S -m dashboard.release_check \
  --bundle-root "$PWD" \
  --expect-revision REVIEWED_COMMIT_SHA \
  --expect-inventory-sha256 REVIEWED_INVENTORY_SHA256
```

The helper uses only Python's standard library; `-S` disables site packages, and
`-B` prevents bytecode-cache writes. No portal credentials or other application
environment variables are needed. Run trusted checker/runtime code; do not
execute an unknown bundle merely to inspect its own assertions. The helper itself
reads but never imports or executes the selected source files. It opens no SQLite
database, creates no run/decoys, starts no server, runs no subprocess/Git,
installs nothing and makes no network calls.

- Exit `0`: selected source matches the supplied revision and inventory digest.
- Exit `1`: inspection blocked or a source/metadata/digest mismatch occurred.
- Exit `2`: malformed/missing CLI options, with private argument values omitted.

Output uses fixed check IDs and validated commit/hash values, not filesystem paths,
environment secrets, arbitrary inventory prose or raw exceptions. Preserve the
JSON alongside the workflow URL, original bundle digest, VM/architecture and
Patrick's separate disconnected-install test record. It is diagnostic metadata,
not a replacement for approved evidence handling.

## What it checks

Inventory bytes must match the externally supplied digest before JSON parsing.
Duplicate fields, unknown/malformed commit identifiers, missing/extra/duplicate
source records, unexpected paths, inconsistent revisions/destinations and invalid
hashes fail. The six source trees are exactly those from the current builder:
`modules`, `dashboard`, `citef-config`, `shared`, `orchestrator`, `schemas`.
The source root may contain no other entries.

For each tree, the helper independently reproduces the builder's sorted relative
path + NUL + binary file SHA-256 directory digest. Changed, missing or added files
fail; symlinks, hardlinked files and special files are rejected, including empty
symlinked directories. Empty ordinary directories are not represented by that
existing digest. Inventory is capped at 2 MiB; each tree at 10,000 entries, depth
32 and 128 MiB of file bytes; each file at 64 MiB. Unreadable or oversized inputs
fail with safe blockers. Detected changes during a file read fail too.

Use a pristine, immutable copy with no concurrent changes. This is not a lock,
filesystem snapshot or future guarantee. Generated bytecode/extra source files
also change the digest: if a previous smoke test wrote caches, use a fresh matching
extraction for this pre-start check. The checker does not delete or normalize them.
The current bundle installation procedure also installs Ansible collections into
`source/citef-config/collections`, changing that source tree. Run this checker
after extracting the trusted runtime but **before** that collection installation,
or against a separate pristine extraction. It does not inspect or remove installed
collections and is not a post-install attestation.

## Explicit non-claims and owner boundary

`source_verified=true` means **selected-source consistency only**. Output always
keeps source authenticity, running-process verification and external readiness
false. It does not verify:

- Archive bytes, portable runtime, wheels/locks or Ansible collection archives.
- The code/bytecode actually loaded by an already running process or service path.
- Runtime configuration, readiness, dependencies or successful offline installation.
- Installer hashes/licences, Windows/Sysmon, Splunk ingestion/RBAC/retention/volume.
- VM architecture/topology/network isolation, DNS/NTP or clean snapshot restores.
- Representative participant usability, rubric calibration or client acceptance.
